## 1. 项目概览

**AI Engineering Atlas** 是一个**交互式 AI 系统工程知识地图 / 教学演示平台**。它将现代 AI 工程（提示工程、RAG、Agent、记忆、MCP、评估、可观测性等）以"可交互的演示节点（Demo Node）+ 路线图（Roadmap）"形式呈现，面向学习者与工程师。

核心特征：

- **纯前端（Client-First）**：所有页面与交互均为客户端组件（`"use client"`），无服务端渲染数据获取、无数据库。
- **模拟式交互（Simulated）**：演示中的"模型生成/推理"大多由 `setTimeout` + 预置文案模拟（例如 `prompt-optimizer` 的 `handleGenerate`），**不调用真实 LLM API**。
- **暗色优先的设计系统**：基于 `next-themes` + shadcn/ui (new-york 风格) + Tailwind CSS v4。
- **静态导出**：`next.config.mjs` 配置 `output: "export"`，产物输出到 `dist/`（注意：不是默认的 `out/`）。

## 2. 技术栈

| 领域 | 选型 |
| --- | --- |
| 框架 | Next.js 15（App Router，RSC 启用） |

```json
  "start": "next start",
  "lint": "next lint"
```

## 5. 数据层（`lib/`）

### 5.1 `lib/demos.ts`
演示节点的**单一注册表**。每个节点含字段：`id`、`title`、`description`、`category`、`icon`、`accent`（主题色）、`difficulty`、`estimatedTime`、`tags` 等。首页的 `DemoCard` 网格、`DemoBrowser` 筛选、`DemoShell` 头部均从此读取。

**新增演示的必做项**：在 `demos.ts` 中追加一条记录，否则首页不会显示（但 `/demos/<id>` 仍可手动访问）。

### 5.2 `lib/mock-auth.tsx`
模拟认证，基于 React Context + `localStorage`：

- 导出 `MockAuthProvider`、`useMockAuth()`。
- 状态：`user`（当前用户）、`isAuthenticated`、`isLoading`。
- 方法：`signIn(email, name?)`（写入 localStorage key `mock-auth-user`）、`signUp(...)`、`signOut()`、`requireAuth()`（未登录跳转登录页）。
- **无密码校验、无真实账号体系**，仅做演示态切换。

### 5.3 `lib/mock-store.ts`
全局应用状态，基于 React Context：

- 导出 `MockStoreProvider`、`useMockStore()`。
- 状态集合：
  - `users: Record<string, User>` — 注册用户（主键 `email`）。
  - `progress: Record<string, Record<string, number>>` — 每用户各演示完成度（0–100）。
  - `bookmarks: Record<string, string[]>` — 每用户收藏的演示 id 列表。
  - `streaks: Record<string, number>` — 连续学习天数。
- 方法：`registerUser`、`updateProgress`、`toggleBookmark`、`recordVisit`（用于计算 streak）、`getUserStats` 等。
- 全部持久化到 `localStorage`（key 如 `mock-store` / `mock-bookmarks` 等）。

### 5.4 `lib/rag-data.ts` + `lib/rag-logic.ts` + `types/rag.ts`
为 RAG 类演示（如 `rag-decision`、`multimodal-rag`、`graph-rag`）提供**静态模拟知识库**：

- `rag-data.ts`：导出 `MENU_INDEX`（菜品知识库）、`HISTORY_INDEX`（用户历史）、`USER_ID` 常量及 `MenuItem`/`HistoryItem` 接口。
- `rag-logic.ts`：导出 `simulateRetrieval(query)`（关键词过滤 + 元数据过滤 + 个性化排序）与 `generateRecommendation(...)`（基于检索结果生成"推荐理由"，含个性化决策逻辑，如"历史吃辣胃不适 → 推荐清淡"）。
- `types/rag.ts`：`RagState` 类型（`query` / `retrievalData` / `generationResult`）。

> 这些是教学用的最小化 RAG 仿真，帮助理解"检索 → 生成"流程，**不接向量库**。

### 5.5 `lib/utils.ts`
shadcn 约定工具，核心是 `cn(...)`（`clsx` + `tailwind-merge`）用于条件类名合并。

## 7. 状态管理与认证（含漂移说明）

```
<MockAuthProvider>          // 认证态：user / isAuthenticated
  <MockStoreProvider>       // 业务态：users / progress / bookmarks / streaks
```

## 11. 开发指南：新增一个演示节点

遵循 `docs/demo-template.tsx` 的模板（已与 `prompt-optimizer` 实际模式对齐）：

1. **复制模板**：`cp docs/demo-template.tsx app/demos/<your-id>/page.tsx`。
2. **填充内容**：替换 `demoData`、各 Tab 文案、`simulateDemo()` 交互逻辑；按需在 `components/` 新建 `*Playground` 子组件。
3. **登记元数据**：在 `lib/demos.ts` 追加 `{ id, title, description, category, icon, accent, difficulty, estimatedTime, tags }`，否则首页不展示。
4. **外壳包裹**：页面最外层用 `<DemoShell demoId="<your-id>">` + `<DemoHero demoId="<your-id>" ... />`，自动获得标题、分类徽章、返回链接。
5. **互链（推荐）**：在相关演示页用 `AtlasTechniqueCarrier` 或 `Link` 建立反向互链，保持内容网络一致。
6. **静态合规**：所有交互必须客户端完成（无 `fetch` 真实后端）；如要"模拟生成"，用 `setTimeout` + 预置文案（参考 `prompt-optimizer` 的 `handleGenerate`）。

## 14. 产品差异化轴心：五种现有形式的结构性天花板与 Atlas 路线

> 本节记录产品定位层面的核心判断：Atlas 与图文 / 视频 / PDF / 一对一 / IDE demo 这五种主流形式的**本质差异在哪**、**该往哪个方向真正"不一样"**。属于战略锚点，与技术实现（第 1–13 节）互为表里。
> 记录时间：2026-07-29。

### 14.1 先立一个前提：这五类形式的局限是结构性天花板，不是"做得不够好"

再怎么优化也翻不过去。搞清楚天花板具体卡在哪，才知道 Atlas 该往哪个方向使劲。

| 形式 | 结构性天花板 |
| --- | --- |
| 图文 / PDF | **单向、静态、无反馈**——读者读完不知道自己有没有真的懂，因为没有任何"验证"环节，只能靠自我感觉 |
| 视频 | **线性、被动**——想跳到自己卡住的那个具体点很难，只能从头拖进度条；而且看别人操作和自己动手，记忆效果差一个数量级 |
| 一对一辅导 | **不可规模化**——效果好，但贵、稀缺、质量完全取决于老师个人水平，没法沉淀成一套"任何人都能重复获得同等体验"的系统 |
| IDE 写 demo | **有真实感，但零散、无体系**——写一个 demo 能学到那一个 demo 的东西，但不会自动知道"这个技巧下一步该学什么、跟其他技巧什么关系"，而且大部分人写完就扔在角落，没人回头系统整理 |

**它们的共同根本问题**：这五种形式都没办法回答"我学完之后，到底能不能自己复述这套系统是怎么运作的、能不能在新场景里自己判断该用哪个方案"——它们要么给你"看 / 听"的体验，要么给你孤立的一次性"做"的体验，但都没有把"系统性理解"当作一个可以被验证、被追踪的东西来设计。

### 14.2 真正的差异化轴心：不是"形式"，是"理解是否可验证 + 知识是否可导航"

Atlas 这几周的设计（T0–T3 阶梯、组件库反向链接、PPT 感→可演练、Engineering Spec Tab、跨案例机制复用、轻量诊断）本质上都在同一条轴线上使劲，串起来看有五条：

**1. 可导航，不是可翻阅**
T0–T3 阶梯 + 组件库的反向链接，让读者能从任何一个具体案例出发，一路"点"回到底层机制，再"点"到其他用了同一个机制的案例——这是一张网，不是一本书。PDF / 视频是"从头到尾"的结构，Atlas 是"从任意一点出发都能找到路"的结构，这是图文类形式天生做不到的。

**2. 可操作，而且操作有真实后果**
"PPT 感→可演练"——拖动滑块看注意力权重实时变化、故意弄坏一个系统看失败模式、调整权重看合规风控的判定结果变不变——这是视频永远给不了的东西：**视频是别人的手在动，Atlas 是你自己的手在动，而且系统会诚实地告诉你操作的后果**。这一点连很多"交互式教程"网站都做不到，因为大部分所谓"交互"其实只是换个页面看结果，不是真的参数联动。

**3. 可复用，知识不是孤岛**
同一个"约束 / 意图识别"机制，能在 RAG 决策和合规风控里被同时引用，读者能亲眼看到"哦，原来这个东西不是这个案例专属的，是个通用积木"。IDE demo 做不到这一点，因为写 demo 的人通常不会专门整理"我这段代码里其实复用了哪些跨项目的通用模式"。

**4. 可复制进代码，不是可复制进笔记**
`Engineering Spec` 这个 Tab 的设计意图，就是让内容不只是"学完了、懂了"，而是**可以直接抄进项目代码 / 架构文档里当参考**——这是"知识"和"资产"的区别。图文类内容抄下来的是别人的表述，Engineering Spec 抄下来的是可执行的规范条目。

**5. 可验证，不是自我感觉良好（尚未实现，待补）**
现有五种形式都没有"你真的懂了吗"这个环节。可考虑在每个节点末尾加一个**轻量诊断**：不是传统的选择题考试，而是"给你一个新的、没见过的场景，让你判断该用哪种方案 / 预测系统会怎么处理某个边界情况"，答对了系统告诉你"你已经内化了这个机制的判断逻辑"，答错了直接跳回具体哪个环节的交互演练重新体验。这比"读完点确定"的图文体验多了一层"真实反馈闭环"，也是一对一辅导里"老师会追问你有没有真的懂"这个环节的规模化替代方案。

### 14.3 代价提醒：这条路"做得慢"，进度衡量指标要换

图文 / 视频 / IDE demo 之所以是主流，是因为**产出速度快**——写一篇文章、录一段视频、写一个 demo，单位时间产出的"内容量"远高于做一个真正可交互、可验证、可复用的知识节点。Atlas 选择的这条路，本质是**用更高的单节点成本，换取"学完之后真的建立体系"这个别人给不了的效果**。

**衡量指标必须换**：
- 不要用"覆盖了多少个知识点"衡量进度。
- 要用"每个上线的节点，是否真正做到了**可操作、可验证、可复用**这三条"衡量。
- **宁可 26 个节点里先有 5 个做到位，也不要 26 个都停留在图文换皮的层面**。

这与第 11 节的开发节奏一致：先挑 2–3 个旗舰节点做透、沉淀成规范，再回填其他节点，而不是全面铺开——铺开的诱惑力在于"看起来内容多"，但这恰恰是在往"碎片化"那条老路上滑回去。
